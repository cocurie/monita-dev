# firmware_child — アイペック案件 Flex②

**派生元: `case01_Flex/v3.20`**（LoRaダウンリンク受信対応版）。
熱電対対応は選択肢を増やすと v3.20 の分岐が肥大するため、**v3.20 本体には入れず本フォルダで個別実装**した。
**`case01_Flex/v3.20` および `case01_Flex/v3.10_lora` は一切変更していない。**

対象ハード: **Monita Flex v3.20 基板**（XIAO nRF52840）
対向 Gateway: `project13_ipec/firmware_gateway/`（`case02_Gateway/firmware/gateway_v1.20` ベース）

---

## チャンネル構成

| CH | センサ | `CH_ASSIGN` | 経路 |
|----|--------|-------------|------|
| CH1 | ひずみゲージ（120Ω） | `1` | HX711（4052 MUX 経由） |
| CH2 | ひずみゲージ（120Ω） | `1` | HX711（4052 MUX 経由） |
| CH3 | **ひずみ式変位計**（ワンタッチ丸型コネクタ） | `1` | HX711（4052 MUX 経由） |
| CH4 | **T型熱電対** | `5` | MCP9600/9601（TCA9546A 経由 I2C） |

```c
const uint8_t CH_ASSIGN[4] = {1, 1, 1, 5};
```

ひずみゲージと変位計は**どちらも HX711 経由で計測経路が同一**のため `CH_ASSIGN` は同じ `1`。
違いは換算係数だけなので、`STRAIN_SCALE[]` を CH 別配列にして吸収する（下記）。

## v3.20 からの差分

| # | 内容 |
|---|------|
| 1 | MCP9600/9601 ドライバ一式を `case01_Flex/v3.10_lora` から移植 |
| 2 | **K型 → T型**：`SENSORCONFIG` を `0x03` → `0x23` に。`MCP9600_TC_TYPE` でビルド時変更可 |

| 6 | `DEVICE_ID` 既定を `0x0E` → **`0x0F`**（`0x0E` は既存の iPEC 実機テスト機が使用中） |
| 7 | `FW_VERSION` を **1 にリセット**（本ファーム独自の連番。v3.20 の番号とは無関係） |

## 熱電対（MCP9600 / MCP9601）

### タイプ設定

`SENSORCONFIG` レジスタ bit6-4 が熱電対タイプ選択。

```
000=K / 001=J / 010=T / 011=N / 100=S / 101=E / 110=B / 111=R
シフト済み: K=0x00 / J=0x10 / T=0x20 / N=0x30 / S=0x40 / E=0x50 / B=0x60 / R=0x70
```

本案件は **T型** なので `0x20`、フィルタmid `0x03` と合わせて **`SENSORCONFIG = 0x23`**。

ビルド時に変更できる:

```sh
PLATFORMIO_BUILD_FLAGS="-D MCP9600_TC_TYPE=0x00" pio run -t upload   # K型で焼く
```

起動ログに実際に書き込んだ値と型名が出るので、**実機で型を取り違えていないか必ず確認すること**。

```
[MCP9600] SENSORCONFIG=0x23 (T型)
```

### 移植元に記録されている実機の注意点

移植元（`v3.10_lora`）のコメントをそのまま引き継いでいる。いずれも実機トラブルの記録なので削らないこと。

- **I2C クロックを 10kHz に落とす**：標準100kHz でのアクセスが NACK（err=2）で一貫して失敗する事象を確認。
  `project06_yokogawa/ver1.1`（本番稼働実績あり）のビットバング I2C 相当（約10kHz）に合わせている。
  MCP9600 アクセス中だけ落とし、終わったら 100kHz に戻す
- **`SENSORCONFIG` 書込直後に `delay(20)`**：内部処理でビジーになり、間髪入れずに次の通信をすると NACK になる
- **アドレスはスキャンで検出**（0x60〜0x67）：基板実装により変わるため固定決め打ちにしない。
  書き込みプローブでは NACK になるため**読み取りプローブ**（`requestFrom`）を使う
- **TCA9546A 切替後に `delay(500)`**：切替直後すぐだと検出できない実機事例がある
- **変換完了はフラグをポーリング**：電源投入直後はフィルタ収束に時間がかかるため固定 delay では足りない

### ⚠ 未検証：MCP9601 の断線検知はT型でも誤報するか

`case01_Flex/test_sketches/15_mcp9600` に、MCP9601 の VSENSE による断線(OC)検知の実測メモがある。

> VSENSE ノードは高インピーダンス（約338kΩ）でノイズを拾いやすく、正常時16.9%VDD に対し
> OC 判定閾値19%まで約69mV しか余裕がない。裸接合の熱電対を手で握った状態では **OC フラグ生起率が約38%**。
> 3回デバウンスでは誤警報がすり抜けたため **10回** に設定。ただしこれは対症療法で、
> 根本対策は**モジュール ver1.1 での平衡コモンモードコンデンサ追加**。

**T型でも同様の傾向が出るかは実機で確認すること。** 本ファームは移植元と同じく `DEVICECONFIG = 0x80`
（バーンアウト検出無効）で動かしているため、現状 OC フラグは参照していない。
断線検知を有効にする場合は上記デバウンスの実装も併せて移植すること。

## ひずみ換算係数（キャリブレーション）

```c
static const float STRAIN_SCALE[4] = {1110.0f, 1110.0f, 1110.0f, 1110.0f};
```

初期値は全CH同じ（v3.20 の実測値）。**CH3 の変位計は感度が異なるため、キャリブレーション後に
その CH だけ別係数にする**ことを想定している。配列にしてあるのでソース構造を触らずに変更できる。

手順（v3.20 から変更なし）:

1. 係数を `1.0f` にして生値をシリアルモニタで確認
2. 既知の荷重／変位を与え、生値の変化量を記録
3. `係数 = 生値変化量 / 既知量` を設定

> 変位計の型番・ブリッジ構成・定格出力（mV/V）は**先方に確認中**。判明したら係数の目安を追記する。

## ビルド・書き込み

```sh
cd project13_ipec/firmware_child
pio run
pio run -t upload
```

### DEVICE_ID の焼き分け

```
DEVICE_ID (1バイト)
  上位3bit = Gateway群 (0〜7)      → group   = DEVICE_ID >> 5
  下位5bit = 群内の機器番号 (1〜31) → localNo = DEVICE_ID & 0x1F   ※0は無効値
```

群は「1つの現場に Gateway を複数台置いたときの二重受信対策」。E220 の無線設定は全機共通のため、
DeviceID の上位3bit でソフトフィルタして受信を分離する。**Gateway 側の `GATEWAY_GROUP_ID` と揃える**こと。

本案件は現場に Gateway 1台のみのため **群0** を使う。

| 機体 | DEVICE_ID | 備考 |
|------|-----------|------|
| Flex①（ひずみ4CH） | 群0の空き番号 | `case01_Flex/v3.20` をそのまま焼く（本フォルダは使わない） |
| **Flex②（本ファーム）** | **`0x0F`**（群0・機器15） | 既定値。`0x0E` は既存の実機テスト機が使用中 |

```sh
PLATFORMIO_BUILD_FLAGS="-D DEVICE_ID=0x0F" pio run -t upload
```

### Flex①（ひずみ4CH）の焼き方

Flex① は**本フォルダを使わず** `case01_Flex/v3.20` をそのまま焼く（`CH_ASSIGN={1,1,1,1}` が既定）。

```sh
cd case01_Flex/v3.20
PLATFORMIO_BUILD_FLAGS="-D DEVICE_ID=0x0D" pio run -t upload   # 番号は空きに合わせる
```

## 触ってはいけない箇所

| 対象 | 理由 |
|------|------|
| `computeWdtTimeoutMs()` の自動計算 | `ACTIVE_SLEEP_MINUTES + WDT_MARGIN_MINUTES` から算出。固定値に戻すと送信間隔との食い違いで無限リブートの危険（CLAUDE.md §7、2026-08-07 の実例） |
| `setup()` 内の `wdtInit()` の呼び出し位置 | 必ず `loadSettings()` の**後**。先に呼ぶと復元前の初期値でタイムアウトを張ってしまう |
| `SLEEP_MINUTES = 60` | 本案件の計測間隔は1時間に1回。既定のまま |
| LoRa ペイロード形式（19バイト、`[13]Hour`/`[14]Minute`） | Gateway 側と対。変更する場合は両方同時に |
| ダウンリンク受信・`ds3231SetTime` による時刻同期・`s_settings` のフラッシュ保存 | v3.20 の機能をそのまま維持 |

## バージョン管理

`main.cpp` を変更して commit する際は `FW_VERSION` を +1 する（CLAUDE.md §6）。
コメント・ログ文言のみの修正は +1 不要。送信間隔・WDT・レジスタ設定値・ペイロード形式など
**実機の挙動に影響する変更は必ず +1**。

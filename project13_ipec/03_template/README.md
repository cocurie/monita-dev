# 03_template — Monita 雛形（検証版）

アイペック案件（project13_ipec）で実機検証した通信方式を土台に、**案件ごとに書き換える箇所を1か所に集めた雛形**。
ここで**ダウンリンクによる設定変更とアラート通知**を確認し、うまくいけば Flex・Gateway の最新ファームとして本流へ移行する。

| フォルダ | 元にしたもの | 版 |
|---|---|---|
| `gateway/` | `project13_ipec/firmware_gateway`（FW14、実機で通信24回連続成功） | **FW24**（Gateway の7コマンド実行・停止状態の flash 保存・ステータス／診断ログ送信を追加。起動時に機器情報を GAS の「Gateway起動ログ」シートへ記録。起動時に LTE-M へつながらなければ診断表示→モジュールとマイコンを再起動。GAS の結果本文を確認し、失敗分を次のサイクルで再送。InfluxDB・iPEC の時刻を UTC に修正。子機ごとに最大6件ためてまとめて送る。シートから送信間隔を変更できる） |
| `child/` | `case01_Flex/v3.10_lora`（FW10）＋ firmware_child（v3.20系）のダウンリンク受信 | **FW13** |
| `gas/` | `project13_ipec/gas/Code.gs`（doPost・ダウンリンク・アラート） | — |

元のファイル（firmware_gateway / firmware_child / v3.10_lora / v1.21 / gas）は変更していない。

## このバージョンで変わったこと

### 可変長ペイロード `0x06`（子機 → Gateway）

| バイト | 内容 |
|---|---|
| [0] | 種別 `0x06` |
| [1] | DeviceID |
| [2] | FW バージョン |
| [3] | チャネル数 n（1〜12。Flex は最大4） |
| [4 .. 3+2n] | CH1〜CHn（int16 LE）。**`0x8000` = 欠測** |
| 続く2バイト | 電池電圧 |
| 最後の2バイト | 時・分。**`0xFF` = 時刻無効** |

従来の `0x04`（19バイト固定）では、センサーの読み取り失敗が `CH=0`、RTC の失敗が `TIME=0:0` になり、**本物の値と区別できなかった**。`0x06` では欠測は空欄、時刻無効は計測日時の空欄としてシートに入る。
Gateway は `0x04` も引き続き受け付けるので、旧ファームの子機と混在できる。

### ダウンリンク（GAS → Gateway → 子機）

- Gateway: gateway_v1.21 の送信処理を移植（予約の取得・子機の受信窓に合わせた送信・子機の確認応答・GAS への報告）
- 子機: firmware_child（v3.20系）の受信窓と確認応答を v3.10 に移植。**送信間隔・平均回数・メジアン回数**を変更でき、flash に保存される（再起動後も保持）。送信間隔が変わると WDT を張り直すため子機は自分で再起動する
- **Gateway が LTE 通信中に子機のアップリンクを受けた場合は送らず、次の起床に回す**（通信中に LoRa へ書き込むと LTE モジュールとのやりとりが壊れるため。v1.21 と同じ）
- **アップリンク検知から送信までの待ち時間を 400ms → 1200ms に変更**。v1.21 の 400ms は1回だけ送信する検証用子機で測った値で、2回送信する子機（v3.20・本雛形）では受信窓が開く前（子機の受信が止まっている間）に届いてしまう計算になるため。**机上の計算なので、実機でここを最初に確認する**

### 子機ごとに複数件ためて送る（FW18〜）
- FW17 までは子機1台につき最新の1件だけを持ち、1サイクルに同じ子機から2回届くと前の計測が上書きで消えていた
- FW18 は子機ごとに最大 `RECORDS_PER_DEVICE`（6）件ためる。FW21 では子機ごとの直近フレームを送信バッファと別に保持し、冗長送信（同じフレームを約0.3秒あけて2回）は「10秒以内・同じ内容」の場合だけ破棄する。送信直後でも判定でき、内容が違えば新しい計測として残す。あふれたら古い1件を捨て、累計の「あふれ破棄」に数える
- InfluxDB は1サイクル1回の POST（行プロトコル複数行）。各点に Gateway の受信時刻（秒）を付ける。**seq は新しい計測を取り出したサイクルだけで数える**（FW17 までは空のサイクルでも増えたため、Gateway の間隔が子機より短いと seq に欠番ができ、送信失敗と区別できなかった）
- GAS へは各件に `rx`（Gateway 受信時刻）を載せる。シートに「**Gateway受信日時**」列を足すとそこに入る（無ければ捨てる）
- iPEC へは従来どおり1件ずつ送る（まとめ方は先方の仕様確認待ち）

### 送信結果の確認と再送（FW21〜）
- GAS の転送先は `https://script.googleusercontent.com`（ポートなし、または443）だけ許可する。直接200が返った場合はエラーページの可能性があるため失敗扱い
- 計測の送信は結果ページを GET し、本文 `ok:<書いた件数>[ dup:<重複件数>]` の合計が送った件数と一致したときだけ成功。子機ダウンリンクの報告も本文が `ok` または `stale` で始まることを確認してからキューを消す
- 失敗した分は GAS・顧客送信先（InfluxDB）ごとに最大 `RETRY_MAX`（96）件残し、次のサイクルで今回分と一緒に送り直す。あふれたら古いものから捨て「再送あふれ」に数える。送信先ごとの対象が0件なら POST・成否集計を行わない
- InfluxDB は同じ点（同タグ・同時刻）を上書きする。GAS は「子機ID＋Gateway受信日時(rx)」で、同じ POST 内の重複、6時間のキャッシュ、書き込み先シートの最後の300行を確認する。キャッシュが空でも既存行で検出できる（「Gateway受信日時」列が必要）。書き込みを `flush()` してからキャッシュに登録する
- 冗長フレームの判定は送信バッファから独立し、同じ子機・10秒以内・内容一致の場合だけ破棄する（RSSI は比較しない）
- 再送分の seq は最初に取り出したサイクルのまま。新しい計測が無く再送分だけのサイクルでは seq を増やさない
- GAS の一括変更は最終状態と途中状態の容量を検証する。必要なら**子機の完了後に Gateway を予約／Gateway の適用確認後に子機を予約**する2段階適用。子機が失敗・予約入替になれば保留を中止し、子機の予約途中で失敗した場合は今回分を取り消す
- iPEC は重複の扱いが先方仕様待ちのため再送しない
- **GAS を先にデプロイしてから FW21 を書き込むこと**（古い GAS はシート既存行による重複判定や2段階適用に未対応）

### Gateway の送信間隔の変更（FW17〜、「Gateway設定」シート）
- **ルール: Gateway の送信間隔 ≦ 子機のいちばん短い送信間隔 × 5**（ためられる6件から、子機の送信ずらしによる1件分の余裕を引いた数）
- 群全体でも `Σ(ceil(Gateway間隔 / 子機間隔) + 1) ≦ 96` を満たす必要がある（+1 は送信ずらしの余裕）
- GAS がシート・URLの予約で両方向を止める: Gateway を上限より長く予約できない／子機を「Gateway の間隔 ÷ 5」より短く予約できない（子機は「確認済みの値」と「予約中の値」の両方を判定対象とし、Gateway は「現在値」と「予約中の値」の長いほうで判定）
- Gateway は毎回の予約確認（check_cmd）に現在の間隔 `gw_interval` を載せる。GAS は予約値と一致したら完了にする（個別の確認応答は不要。報告が落ちても次の確認で確定する）
- Gateway は受け取った `interval:N` を flash に保存してから適用し、アプリ層 WDT（2.5倍、ただし最低でも送信間隔＋10分）も新しい間隔で数え直す（CLAUDE.md §7）。**flash の値はファームを書き直しても残る**（project_config の既定に戻すにはシートから入れ直す）

### Gateway 操作（FW24〜）

「Gateway設定」シートの「Gateway操作」欄でチェックすると予約する。スタンドアロン GAS なのでメニューではなく、インストール型編集トリガー `onDownlinkSheetEdit` を使う。

| 操作 | コマンド | 動作 |
|---|---|---|
| リモートリセット | `reset` | ack 成功後に再起動。RAM の再送待ちデータは消える |
| データ送信を停止 | `stop` | 定期的なデータ送信を停止。LoRa 受信・蓄積・子機のダウンリンク・予約確認は継続 |
| データ送信を再開 | `start` | 定期的なデータ送信を再開 |
| 今すぐ送信 | `send_now` | 停止中でも、蓄積分と再送待ちをその場で1回送信 |
| ステータス確認 | `status_now` | 時刻・送信状態・電波強度・バッファ・通信成否などを「Gatewayステータス」に追記 |
| RTC再同期 | `rtc_resync` | 網時刻で RTC を補正し、その後ステータスを報告 |
| 診断ログを吸い上げ | `log_dump` | RAM の直近24件を古い順で「Gateway診断ログ」に追記（送信後もログは保持） |

- 7コマンドは **`ack_cmd` の結果本文が `ok` で始まることを確認してから実行**する。特に `reset` は ack 前に再起動すると予約が残り、無限リセットになる。ack 失敗時は実行せず、次のサイクルに持ち越す。間隔変更は従来どおり `gw_interval` の報告で完了する。
- **予約枠は1つ**。別のコマンドがあるときは上書きできない（間隔→間隔の変更は可能）。「現在の予約」を確認し、完了を待つか「予約を取り消す」を使う。Gateway の一括変更の保留も取消で中止する。
- 操作は次の予約確認で実行するため、最大で現在の送信間隔ぶん待つ。「完了」は Gateway が受け取ったことを示す。
- **停止状態は flash に保存され、再起動後も継続**する。「データ送信を再開」で戻る。停止中も容量を超えた古い計測は捨てる。
- 「送信の状態」は直近のステータス報告を表示する。停止・再開後は「ステータス確認」で更新する。
- 更新時はエディタで **`setupGatewayBlock` と `upgradeDownlinkBlocks` を再実行**する。既存の設定欄を残して Gateway 操作欄と子機の「予約を取り消す」を追加する。編集トリガー未登録なら `installDownlinkEditTrigger` も実行する。

### その他
- Gateway の RTC を起動時（年が2026未満または電源喪失時）と24時間ごとに網時刻（JST）で補正
- アプリ層 WDT は送信間隔の 2.5倍（ただし最低でも送信間隔＋10分）（1回の全経路失敗で再起動しない）
- 顧客サーバーの API キーはソースから `secrets.h` へ移動

## 検証手順

### 1. 通常送信（0x06）
- 子機ログ: `[LORA] TX 0x06 FW=11 n=4 CH=… TIME=…` の後に `[DOWNLINK] RXウィンドウ開始 2000ms...`
- Gateway ログ: `[LORA RX] #1 0x6 ID=0xE n=4 CH=…`
- シート: CH1〜CH4 に値。読み取りに失敗したチャネルは空欄（従来は 0）

### 2. ダウンリンク（送信間隔の変更）
1. 予約する。
   - スクリプトがスプレッドシートに紐付いている場合: メニュー「Flex操作」→「送信間隔を変更」→ DeviceID `0E` → 例: `3`（分）
   - **スタンドアロンのスクリプトの場合（メニューが出ない）**: `Code.gs` の `EDITOR_DL_*` を書き換えて保存し、エディタで `editorDlSetInterval` を実行する（デプロイし直しは不要）。状態は `editorDlShow` で確認できる
2. Gateway の次の送信サイクルで予約を取得: `[DOWNLINK] 予約: 子機0xE 間隔=3分 …`
3. 子機の次のアップリンクで送信: `[DOWNLINK] 子機0xE のアップリンクを検知（1回目/3）→ 1200ms待ってから送信`
4. 子機: `★自分宛ての有効なコマンドを受信` → `確認応答を送信` → `WDTを再設定します。再起動します`
5. Gateway: `★子機0xE から確認応答: status=0 適用値 間隔=3分 …`
6. Gateway の次の送信サイクルで GAS へ報告: `[REPORT] … 成功`
7. シート `cmd_status` の結果が「完了」、`設定変更履歴` に予約→送信→結果が並ぶ

完了まで最大で「Gateway の送信間隔 ＋ 子機の送信間隔 ＋ Gateway の送信間隔」程度かかる。
Gateway が通信中に子機のアップリンクが来た場合は `AT通信中のため次サイクルに見送ります` と出て、もう1周期かかる（正常）。

同じ手順で「平均/メジアン回数を変更」（`editorDlSetAvgMedian`）「ステータス確認」（`editorDlStatusCheck`、設定を変えずに現在値を返させる）も確認する。
3回送っても確認応答が来ない場合は「未達」として GAS に報告される。

### 2b. スプレッドシートからのダウンリンク（子機シートの「ダウンリンク設定」欄）
スクリプトはスタンドアロンのまま（顧客からコードが見えない）。初回は上記の `setupAllSheets` と `installDownlinkEditTrigger` を実行する。個別に設定する場合:
1. `setupDownlinkBlocks` … 「雛形」と `DL_BLOCK_EXTRA_SHEETS`（既定: `0014`）の Q 列から設定欄を作る（mail-11〜20 の列は片付ける。宛先は10件）
2. `installDownlinkEditTrigger` … チェックボックスで予約する編集トリガーを作る（初回は権限の承認が出る）
3. 設定欄（Q〜S列の1〜12行目）を「範囲の保護」でコクリエのアカウントだけ編集可にする

使い方: 「変更後」に値を入れて（空欄の項目は子機の現在値のまま）「設定を変更する」にチェック → 予約される。
「ステータス確認」にチェックすると、設定を変えずに子機の現在値が返ってくる。状態と現在値は GAS が自動で書き戻す。

### 2c. Gateway の送信間隔（「Gateway設定」シート）
1. Gateway に FW17 を書き込む → 最初の予約確認で GAS が現在値（既定3分）を受け取る
2. エディタで `setupGatewayBlock` を実行 → 「Gateway設定」シートができ、現在値・子機の最短間隔が表示される（編集トリガーは子機と共通）
3. 子機の最短間隔より長い値を入れてチェック → 「入力エラー」になること
4. 子機の最短間隔以下の値を入れてチェック → 状態「予約中」→ Gateway ログ `[GW-CMD] ★送信間隔を変更` → 状態「—」・現在値が新しい値になること（`設定変更履歴` に 予約／変更確認／完了）
5. 子機シートで Gateway より短い送信間隔を入れる → 「入力エラー」になること

### 2d. 一括変更（「Gateway設定」シートの「一括変更（Gateway＋全子機）」欄）
- `setupGatewayBlock` をもう一度実行すると欄が追加される（既存の設定欄はそのまま）
- 子機の送信間隔・平均・メジアン、Gateway の送信間隔を入れて「まとめて変更する」→ 群の全子機と Gateway を1回で予約する。空欄は変更しない
- ルール（Gateway ≦ 子機の最短 × 5）は**変更後の値どうし**で判定するので、個別の欄のような「変える順番」の制約がない
- 現在値が不明な子機があると、子機の3項目すべての入力を求める（既定値で埋めない）。エラー時は何も予約しない

### 3. アラート
- **閾値アラート**: 子機シートの dateKey で、確実に超える閾値（例: CH1 の絶対値 > 1）と自分の宛先を設定 → 次のデータ受信でメールが届くこと
- **未受信アラート**: `ADMIN_MAILS` を設定し、検証中は `NO_DATA_LIMIT_MS` を短く（例: 15分）してデプロイし直す → 子機の電源を切る → トリガーの次回実行でメールが届くこと。**確認後は元の値に戻す**

## 既知の制約・未実装

- **計測日時は子機の時計（時・分）から作っているが、子機の時計は外から正しい時刻をもらう仕組みがない**（2026-09-23 確認）。
  子機は起動時に時計が止まっていると**ビルド時刻**を書き込む（v3.03・v3.10・v3.20 共通）。USB で書き込み（電池なし）→ 現場で電池を挿す、という手順では、
  「ビルドしてから電池を挿すまでの時間」だけずれた時刻が、正しい時刻として送られ続ける。**計測日時は目安として扱い、分析には受信日時を使う**。
  本番 Gateway v1.21 と Sigfox 運用は子機の時刻を使わず、受信時刻を計測日時としているため、これまで表に出なかった。
  現場で正確な計測時刻が必要になったら、Gateway から子機へ網時刻を配る仕組み（子機は DL_FLAG_TIME で受け取れる）を追加する
- 検証中に子機を USB 給電だけで動かすと、DS3231 の VBAT（本体電池 J1 から給電）に電源が来ないため、スリープのたびに時計が 2000-01-01 に戻る（子機は「時刻無効」として送るので計測日時は空欄になる）。現場（電池あり）では起きない
- **Codex レビュー（2026-09-23）で見つかり、まだ直していないもの**
  - 子機が複数台ほぼ同時に送ると、Gateway が1台目に応答するための待ち（約1.5秒、受信処理が止まる）の間に2台目の受信窓を外れることがある。複数台の検証時に実測する
  - センサーの一部の失敗（MUX 切替の失敗、VL53L4CD の測距状態、MCP9600 の変換待ちタイムアウト）が欠測にならず、値として送られる経路がある（v3.10 から引き継いだもの）
- 再送キューは RAM のみ（再起動・電源断で消える）
- iPEC は再送しない
- LTE 断からの段階的復旧は、起動時のみ実装（FW22: 接続失敗→診断表示→SIM7080G とマイコンを再起動）。**運用中に切れた場合**のつなぎ直しは未実装で、アプリ層WDTによる再起動頼み
- シートの行数が1年でセル上限に近づく（アーカイブ未実装）
- HTTP の chunked 終端判定は簡易（通常の GAS・Drive・InfluxDB 応答では問題なし）
- RTC 無効時は rx が付かず重複判定できない
- seq は「新しい計測を取り出したサイクル番号」。同じ起動の全点での欠番はそのサイクル全体が失われたことを意味する（一部欠落は件数で見る）
- 子機は **v3.10 ベース**（手元の基板が v3.10 のため）。本流の v3.20 へ移行する際は、`0x06` の送信と `project_config.h` を v3.20 に同様に入れる（v3.20 はダウンリンク受信を既に持っている）

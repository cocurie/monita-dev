## 1. 製品概要

### 1-1. 用途・位置づけ

| 項目 | 内容 |
|---|---|
| 位置づけ | Monita Flex の低価格版。**1CH に絞り、ソーラーで動かす**無線計測ユニット |
| ねらい | 電池交換の手間を減らす。1か所1CHで足りる計測を安く多点に展開する |
| センサ | Flex 用センサモジュールの端子と互換（ピン配列が同じ） |
| 構成の考え方（v1.1） | 本体は DIP 部品だけの基板。XIAO・無線モジュール・充電モジュールは差し替えできる（レンタルでの使い回しを想定）。出典: v1.1差分 §1〜2 |

### 1-2. 2つの版

| | **標準版（センサ版）** | **PIR版（人数推定版）** |
|---|---|---|
| 何を送るか | センサ1CHの計測値 | 人感センサ（PIR）が反応したときだけ BLE を受信し、周囲のスマホなどの台数から人数を推定する。その集計値を定時に送る |
| 想定用途 | 構造物のひずみ・変位・温度・距離など | 人の少ない公園などの利用状況の把握（PIR要件 §1） |
| 動き方 | 起きる → 計測 → 送信 → 眠る（既定60分周期） | PIR で起きる → BLE を30秒受信して人数を推定 → 集計に加える。60分ごとにまとめて送信 |
| ファーム | `src/app_sensor.cpp` | `src/app_pir.cpp` |

無線は **LoRa か Sigfox のどちらか1つ**を選ぶ。どちらにするかはビルド時に決まり、基板に載せるモジュールも片方だけにする。組合せは 標準/PIR × LoRa/Sigfox の4通り（`platformio.ini:29-44`）。

### 1-3. システム構成

```
 ┌──────── Monita One ────────────────────────────┐
 │ センサ（Flexモジュール）または PIR                │
 │      │ 3V3_SW（MOSFETで入切）                    │

        ▲ ダウンリンク（遠隔設定）
```

## 3. 計測仕様

### 3-1. 標準版: 対応センサ（`CH_ASSIGN`）

`CH_ASSIGN` はビルド時の定数で、ソースに直接書いてある（`src/app_sensor.cpp:35`）。**ビルドフラグでは変えられないので、変えるときはソースを直して再ビルドする。**

| CH_ASSIGN | センサ | 接続 | 送信する値 | 単位 | 実機確認 |
|---|---|---|---|---|---|
| **1（既定）** | HX711（ひずみ・変位） | PD_SCK=D3、DOUT=D4 | §3-2 の換算値 | **未校正（µε ではない）** | v1.00 で計測が動くことを確認（2026-08-26、ロードセル未接続） |
| 2 | LSM6DS（**外付け**。センサ端子の I2C、アドレス 0x6B、104Hz・±2g） | I2C D5/D6 | ピッチ角（小数点以下は切り捨て） | 0.1° | 未 |
| 3 | DS18B20 | PD_SCK を 1-Wire として使う | 温度（四捨五入） | 0.1℃ | 未 |
| 4 | VL53L4CD | I2C D5/D6 | 10回測った距離の中央値 | mm | 未 |

- 区分: すべて設計値（`src/app_sensor.cpp:119-246`）。CH_ASSIGN=2 は XIAO Sense に内蔵の IMU ではなく、センサ端子に付けた LSM6DS を読む（`src/one_hal.cpp:13-15`）。
- CH_ASSIGN の 2〜4 は、One で動かしたことがない。出荷する構成だけ試験する（F-M7 に準じる）。

### 3-2. 標準版: 換算と平均の方法（HX711）

| 項目 | 内容 | 区分 | 根拠 |
|---|---|---|---|
| ゲイン | 128（ライブラリ既定） | 設計値 | `lib/HX711/src/HX711.h:39` |
| 平均の方法 | `samplesPerAvg` 回（既定10）の平均を、`measureCount` 回（既定10）繰り返す。その**中央値**を送る | 設計値 | `src/app_sensor.cpp:39-40,128-149` |
| 換算式 | 値 ＝ Σ(生値 − タレ値) ÷ samplesPerAvg ÷ `STRAIN_SCALE`（整数で切り捨て） | 設計値 | `src/app_sensor.cpp:138,141` |
| `STRAIN_SCALE` | **100（未校正）**。Flex は 1110 | **未確定** | `src/app_sensor.cpp:45`。O-M1 |
| 設定範囲 | samplesPerAvg 1〜255、measureCount 1〜50 | 設計値 | `src/app_sensor.cpp:41,88-89` |
| ばらつき（range） | 中央値を取る前の値の最大 − 最小（0〜255で頭打ち）。LoRa フレームには載るが、Gateway がシートへ渡さない | 設計値 | `src/app_sensor.cpp:150-151`、試験一覧 B-9 |
| タレ（ゼロ点） | 初期値は 0（タレなし）。再タレは LoRa ダウンリンクの bit3 だけで実行できる（10回の平均を保存） | 設計値 | `src/app_sensor.cpp:78,157-172,298-301` |

**表示値の意味（重要）**
- 今の値は「HX711 のカウント ÷ 100」で、**µε ではない**。校正（O-M1）が済むまで、ひずみの単位で説明しない。
- 校正すれば Flex と同じ換算になる見込み。そのときの値は**クォータブリッジ換算**で、**ハーフブリッジでは真ひずみの約2倍**、フルブリッジでは約4倍（理論値）になる（ハーフブリッジの2倍は Flex で確認済み。One では未確認）。仕様書・取扱説明書・報告書にこのことを書く。

### 3-3. PIR版: 検知と人数推定の方式

| 段階 | 動作 | 既定値 | 設定範囲 | 根拠 |
|---|---|---|---|---|
| ① 検知 | PIR の出力（D4）が HIGH になると GPIO の SENSE で起きる（消費の大きい GPIOTE IN は使わない） | — | — | `src/app_pir.cpp:261-315` |
| ② 抑止（holdoff） | 前回のスキャンから一定時間は PIR を無視する | 120秒 | 0〜3600秒 | `:132,145,345-348` |
| ③ 回数の上限 | 1時間に行うスキャンの上限。超えた分は数えるが、スキャンしない | 6回 | 0〜60回（0＝上限なし） | `:133,146,354-358` |
| ④ BLE受信 | パッシブスキャン（本機は電波を出さない）。interval 150ms / window 100ms | 30秒 | 5〜120秒 | `:37-38,134,146,566-568` |
| ⑤ 推定 | 受信強度が閾値以上の信号を `minHits` 回以上受けた端末を数える → 平均受信強度の近い端末（差が `mergeGap` 以内）を1人にまとめる → 人数 × 補正係数（小数点以下は切り捨て） | −65dBm / 10回 / 3dB / ×1.0 | −100〜−40dBm / 1〜50 / 0〜20dB / ×0.1〜×25.5 | `:128-131,143-145,226-248` |
| ⑥ 集計 | 報告期間ごとに、最大人数・人数の合計・スキャン回数・PIR イベント数を数える | — | — | `:317-337` |
| ⑦ 報告 | 決まった間隔で送る。スキャンが0回だった期間も送る（ハートビート）。人数は `-1`（未計測）にする | 60分 | 5〜1440分 | `:127,475-531`、`src/one_payload.cpp:82-84` |
| ⑧ 送れなかった期間 | 集計を捨てず、次の期間に足す（FW 6〜） | — | — | `:390-402,521-522` |
| ⑨ 故障対策 | PIR が10秒以上 HIGH のままなら張り付きとみなして切り離す。LOW に戻れば復帰する | 10秒 | — | `:42,362-371` |
| ⑩ 端末数の上限 | 1回のスキャンで覚える端末は64台まで。超えた分は捨てる（件数は送らない） | 64台 | — | `:36,210-224` |

区分: すべて設計値。**実機（v1.00・v1.1とも）では一度も動かしていない。**

- `scanDurationSec` を変えると `minHits` の意味も変わる。この2つは必ずセットで変える（PIR要件 §6-1）。
- スキャンの時間と回数を上限まで上げると、消費が1日 70mAh を超えるという試算がある（v1.01差分 §E-7）。既定値の近くで使う。

### 3-4. PIR版: 精度の扱い

- 送る値は「**BLE 端末の検出数から推定した人数の目安**」で、人数を数えた値ではない。
- 精度は評価していない（O-M4）。PIR要件にある「初期 ±30〜50%、改善後 ±10〜20%」（§1）や「±20% 以内」（§10-2）は**開発目標**なので、カタログ・提案には載せない。
- 分かっている誤差の原因（PIR要件 §4-2 L1〜L6）
  - 同じくらいの距離に複数の人がいると、1人にまとめてしまう → 混雑すると少なめに出る
  - スマホを持っていない人、BLE をオフにしている人は数えられない
  - 1人が複数の端末を持っている、近くに固定の BLE 機器がある、アドレスが変わる → 多めに出る
- 端末のアドレスは約15分で変わるため、スキャンをまたいだ「延べ人数」「重複を除いた人数」は出さない（PIR要件 §4-2）。

## 7. 操作・運用

### 7-1. 製造（組立・書込み）

| # | 作業 | 注意 |
|---|---|---|
| 1 | **基板と FW を正しく組み合わせる** | v1.1 基板には `case03_One/v1.1`（FW 5以上）、v1.00 基板には `case03_One/v1.00`（FW 0x04）。v1.1 の FW を v1.00 基板に書くと、毎回 AUX 待ちがタイムアウトして起きている時間が延びる（`README.md`、O-B6） |
| 2 | 版と無線に合ったビルド環境を選ぶ | 4つの環境（§2） |
| 3 | **機体ごとに DEVICE_ID を変えて書き込む** | `PLATFORMIO_BUILD_FLAGS="-D DEVICE_ID=0x24" pio run -e one_sensor_lora -t upload`。上位3bit＝Gateway 群、下位5bit＝群内の番号（1〜31。0 にするとビルドが止まる）。何も指定しないと 0x0F になる。**IDが重なるとデータが混ざる**ので、ラベルを機体に貼る |
| 4 | センサの種類を変えるとき（標準版） | `src/app_sensor.cpp:35` の `CH_ASSIGN` を直して再ビルドする |
| 5 | E220 と Sigfox は**片方だけ**載せる | 両方載せると UART の出力どうしがぶつかる（v1.01差分 §C-5） |
| 6 | XIAO の向き | シルクの外形と USB-C の向きに合わせる。逆に挿すとセンサモジュールが壊れる（v1.00 で実際に1枚壊した） |
| 7 | 充電モジュールの向き | 逆向きでは挿さらないよう、受け側の穴を配置している（v1.1差分 §3 #13） |
| 8 | Sigfox モジュールの事前設定 | **FW はモードとリージョンを設定しない**。新しいモジュールには一度だけ `AT+MODE=0` → `AT$RC=3C` → `ATZ` を実行して、送信周波数が 92x MHz になることを確かめる。ID と PAC を Sigfox に登録する（Flex と同じ手順） |
| 9 | R7 の値 | 100kΩ になっているか確かめる（O-B0） |
| 10 | 書込み後の確認 | USB シリアル（115200bps）の `[BOOT]` 行で FW、DEVICE_ID、group、localNo（標準版はさらに CH_ASSIGN と sleepMin）を見る |

## 付録A. 送信データ形式（概要）

整数は、特記なければリトルエンディアン。欠測は `-1`（0xFFFF）。詳しくはペイロード仕様 v1.0 と、`test/host_payload_test.cpp`・`case02_Gateway/tests/monita_one_payload_vectors.test.js`（GV-1〜GV-8。2026-09-24 に両方とも PASS）。

**A-1. LoRa アップリンク 19B（Pkt type 0x04）**。E220 へは `0xAA, LEN, 本体, チェックサム` の形で渡す（`src/one_hal.cpp:209-229`）。

| offset | 型 | 標準版 | PIR版 |
|---|---|---|---|
| 0 | u8 | 0x04 | 0x04 |
| 1 | u8 | DEVICE_ID | DEVICE_ID |
| 2 | u8 | FW 版（6） | FW 版（6） |
| 3–4 | i16 | CH1 計測値 | 最大人数（スキャン0回なら -1） |
| 5–6 | i16 | -1 | 平均人数 ×10（四捨五入。スキャン0回なら -1） |
| 7–8 | i16 | -1 | PIR イベント数 |
| 9–10 | i16 | 充電状態 0〜3 | スキャン回数（bit0〜12、8191で頭打ち）＋充電状態（bit13〜14） |
| 11–12 | u16 | 電池電圧 mV | 電池電圧 mV |
| 13–14 | u8×2 | 0（RTC なし） | 0 |
| 15 | u8 | range（0〜255） | 0 |
| 16–18 | u8×3 | 0 | 0 |

値は int16 の範囲で頭打ちにする（`src/one_payload.cpp:30-46`）。

**A-2. Sigfox 12B（暫定）**: CH1〜CH4（i16×4。意味は A-1 と同じ）、CPU 温度 ×10（i16。**外気温ではない**）、電池電圧 mV（u16）（`src/one_payload.cpp:91-113`）。DEVICE_ID と FW 版は含まない。

**A-3. Gateway → GAS（14B/台、`CLOUD_FMT_V2`）**: epoch（u32）＋ DEVICE_ID ＋ CH1〜CH4（8B）＋ 電池（1B: 0＝3000mV 以下、1〜254＝3000＋5×値 mV、255＝不明）。Gateway は A-1 の offset 13〜18 を送らない。

**A-4. ダウンリンク 15B（LoRa）**: `C0 DE 81 ID flags` ＋ 10B（ビッグエンディアン）

| | 標準版 | PIR版 |
|---|---|---|
| flags | bit0 時刻（非対応）／bit1 送信間隔／bit2 平均・中央値の回数／bit3 再タレ | bit0〜7 がそれぞれ次の8項目に対応 |
| 5–14 | 時刻 6B（年・月・日・時・分・秒）、送信間隔 2B、平均回数 1B、中央値回数 1B | 報告間隔 2B、RSSI 1B、minHits 1B、mergeGap 1B、補正 1B、holdoff 2B、スキャン上限 1B、スキャン時間 1B |

**A-5. 応答（ACK、Pkt type 0x05）**
- 標準版 9B: `05 ID status 送信間隔(2) 平均回数 中央値回数 WDT(2)`
- PIR版 14B: `05 ID status 報告間隔(2) RSSI minHits mergeGap 補正 holdoff(2) スキャン上限 スキャン時間 FW`
- status: 0＝OK、1＝値が範囲外、2＝時刻に非対応

# Monita Gateway / Flex / One DeviceID設定説明書

## 1. この説明書の目的

現場ごと・機体ごとに、Monita Gateway / Flex / Oneを正しいIDで書き分けるための手順書です。
コマンドはすべて`monita-dev`リポジトリのルートで実行します。

書き込み前に、必ずID割当台帳で次の項目を確定してください。

- 現場ID
- Gateway論理名、`GW_DEVICE_ID`（XIAO固有ID）、IMEI、Gateway群
- 子機シリアル、製品種別（`FLEX` / `ONE_SENSOR` / `ONE_PIR`）
- 完全DeviceID、群内番号、設置位置
- FWバージョン、ビルドhash、書込日時、担当者

同じ群の中で同じDeviceIDを2台に割り当てないでください。IDが重複すると、Gateway上で同じ機器として扱われ、後から届いたデータで上書きされることがあります。台帳と機体ラベルの両方に完全DeviceIDを記載します。

## 2. DeviceIDの決め方

DeviceIDは1バイト（8bit）です。

```text
bit位置       7   6   5 | 4   3   2   1   0
             +-----------+-------------------+
意味         | Gateway群 |   群内の機器番号  |
             +-----------+-------------------+
使用範囲     |   0〜7     |      1〜31        |
計算         | ID >> 5    | ID & 0x1F         |
```

下位5bitが`0`になる値は無効です。たとえば`0x00`、`0x20`、`0x40`は使用できません。

完全DeviceIDは次の式で求めます。

```text
DeviceID = (Gateway群 × 0x20) + 群内の機器番号
```

| Gateway群 | 使用できるDeviceID | 対応するGateway |
|---:|---|---|
| 0 | `0x01`〜`0x1F` | `GATEWAY_GROUP_ID=0` |
| 1 | `0x21`〜`0x3F` | `GATEWAY_GROUP_ID=1` |
| 2 | `0x41`〜`0x5F` | `GATEWAY_GROUP_ID=2` |
| 3 | `0x61`〜`0x7F` | `GATEWAY_GROUP_ID=3` |
| 4 | `0x81`〜`0x9F` | `GATEWAY_GROUP_ID=4` |
| 5 | `0xA1`〜`0xBF` | `GATEWAY_GROUP_ID=5` |
| 6 | `0xC1`〜`0xDF` | `GATEWAY_GROUP_ID=6` |
| 7 | `0xE1`〜`0xFF` | `GATEWAY_GROUP_ID=7` |

例：群1の4番は`(1 × 0x20) + 4 = 0x24`です。

## 3. 書き込み前の共通確認

1. ID割当台帳で、対象機のGateway群と群内番号を確認します。
2. 上の式で完全DeviceIDを求め、台帳に記入します。
3. 同じ現場・同じ群に重複がないことを確認します。
4. USB接続する機体が台帳の対象機と一致することを、シリアル番号または機体ラベルで確認します。
5. 下記の該当コマンドをコピーして書き込みます。
6. 起動ログを確認してから機体ラベルへIDを記入します。

`PLATFORMIO_BUILD_FLAGS`は、そのコマンドを実行した1回だけ設定を上書きします。ソースコードや`platformio.ini`を書き換える必要はありません。

## 4. Gatewayの設定と書き込み

GatewayにはDeviceIDではなく、受信対象を決める`GATEWAY_GROUP_ID`（0〜7）を指定します。指定しない場合の既定値は群0です。

群0のGatewayを書き込む例：

```bash
PLATFORMIO_BUILD_FLAGS="-D GATEWAY_GROUP_ID=0" pio run -d case02_Gateway/firmware/gateway_v1.20 -t upload
```

群1のGatewayを書き込む例：

```bash
PLATFORMIO_BUILD_FLAGS="-D GATEWAY_GROUP_ID=1" pio run -d case02_Gateway/firmware/gateway_v1.20 -t upload
```

通信モードは`case02_Gateway/firmware/gateway_v1.20/platformio.ini`の`COMM_MODE_BLE`または`COMM_MODE_LORA`で決まります。現状のファイルは`COMM_MODE_LORA`が有効です。指定する現場仕様と一致していることを、書き込み前に確認してください。

## 5. Flexの設定と書き込み

Flexには完全DeviceIDを`DEVICE_ID`で指定します。`platformio.ini`は単一envのため、先に同ファイルの`build_flags`で対象通信モードを1つだけ選びます。

- BLE：`-D COMM_MODE_BLE`。DeviceID未指定時の既定値は`0x01`（群0・機器1）
- LoRa：`-D COMM_MODE_LORA`。DeviceID未指定時の既定値は`0x0E`（群0・機器14、iPEC実機テスト用）
- Sigfox：`-D COMM_MODE_SIGFOX`。DeviceID設定の対象外

現状の`platformio.ini`は`COMM_MODE_LORA`が有効です。

群0・機器1（`0x01`）を書き込む例：

```bash
PLATFORMIO_BUILD_FLAGS="-D DEVICE_ID=0x01" pio run -d case01_Flex/v3.20 -t upload
```

群1・機器1（`0x21`）を書き込む例：

```bash
PLATFORMIO_BUILD_FLAGS="-D DEVICE_ID=0x21" pio run -d case01_Flex/v3.20 -t upload
```

既定値に頼ると機体間でIDが重複しやすいため、量産・現場書き込みでは毎回`DEVICE_ID`を明示してください。

## 6. Oneの設定と書き込み

Oneには完全DeviceIDを`DEVICE_ID`で指定し、機体用途と無線方式に合うenvを選びます。DeviceID未指定時の既定値は、sensor版・PIR版ともに`0x0F`（群0・機器15）です。

| env名 | 機体用途 | 通信方式 |
|---|---|---|
| `one_sensor_lora` | センサ版 | LoRa |
| `one_sensor_sigfox` | センサ版 | Sigfox |
| `one_pir_lora` | PIR版 | LoRa |
| `one_pir_sigfox` | PIR版 | Sigfox |

群1・機器4（`0x24`）をセンサ版LoRaへ書き込む例：

```bash
PLATFORMIO_BUILD_FLAGS="-D DEVICE_ID=0x24" pio run -d case03_One/v1.00 -e one_sensor_lora -t upload
```

同じIDをPIR版LoRaへ書き込む場合：

```bash
PLATFORMIO_BUILD_FLAGS="-D DEVICE_ID=0x24" pio run -d case03_One/v1.00 -e one_pir_lora -t upload
```

Sigfox版へ書き込む場合は、機体用途に応じて`one_sensor_sigfox`または`one_pir_sigfox`を指定します。Gateway群で受信を分ける運用はLoRa向けですが、Oneの全envで同じDeviceID検証が行われます。

## 7. 無効な値を指定した場合

次の値はコンパイル時の`static_assert`で拒否され、ビルド自体が失敗します。実機へ書き込まれる前に間違いへ気づける設計です。

- Flex / One：`0x00`、`0x20`、`0x40`など、下位5bitが0のDeviceID
- Flex / One：`0x01`〜`0xFF`の範囲外のDeviceID
- Gateway：0〜7の範囲外の`GATEWAY_GROUP_ID`

たとえば、次のOne書き込みは`0x20`の下位5bitが0なので失敗するのが正常です。

```bash
PLATFORMIO_BUILD_FLAGS="-D DEVICE_ID=0x20" pio run -d case03_One/v1.00 -e one_sensor_lora -t upload
```

エラーを避けるために検証を外したり、別の値へ適当に変更したりせず、ID割当台帳を確認してください。

## 8. 1現場にGatewayを2台置く場合の実務例

ここではGateway 2台と複数のLoRa子機を設置する例を示します。

1. 台帳にGateway 1台目を「群0」、Gateway 2台目を「群1」と登録します。
2. Gateway 1台目へ`GATEWAY_GROUP_ID=0`、2台目へ`GATEWAY_GROUP_ID=1`を指定して書き込みます。
3. 群0に接続する子機へ、群内番号を1から順に割り当てます。例：Flex 3台を`0x01`、`0x02`、`0x03`、One 3台を`0x04`、`0x05`、`0x06`。
4. 群1に接続する子機も、群内番号を1から順に割り当てます。例：Flex 3台を`0x21`、`0x22`、`0x23`、One 3台を`0x24`、`0x25`、`0x26`。
5. 子機は1台ずつUSB接続し、台帳の完全DeviceIDを指定して書き込みます。
6. 書き込み直後に起動ログを確認し、台帳と一致した機体だけにラベルを貼ります。
7. 各Gatewayで、自群の子機だけが受信ログへ出ることを確認します。

群番号が違えば完全DeviceIDも異なるため、群0の`0x01`と群1の`0x21`は別の機器として扱われます。ただし、同じ群で`0x01`を2回使うことはできません。欠番は問題ありません。交換機を用意するときも、稼働中のIDを同時に使わないでください。

## 9. 起動ログでの確認

シリアルモニターの速度は各プロジェクトとも115200 bpsです。書き込み後、次のコマンドで対象プロジェクトのログを開けます。

```bash
pio device monitor -b 115200
```

各ファームでは起動時に次の情報が出ます。

- Gateway：`GW_DEVICE_ID`、XIAO固有ID、`Gateway群`、その群が受信する子機DeviceID範囲。群1以上ではダウンリンク無効の案内も出ます。
- Flex：`[ID] DEVICE_ID=0x.. group=.. localNo=..`
- One sensor：`[BOOT] Monita One sensor ... DEVICE_ID=0x.. group=.. localNo=..`
- One PIR：`[BOOT] Monita One PIR ... DEVICE_ID=0x.. group=.. localNo=..`

Gateway自身には子機のような完全DeviceID・群内番号はありません。代わりにGateway群と受信対象範囲を確認します。Flex / Oneでは完全DeviceID、群番号、群内番号の3点を台帳と照合してください。

焼き間違いを検知した場合は、その機体を設置せず、正しいフラグで再度書き込みます。通信確認時はGatewayのLoRa受信ログに`[LORA] フレーム受信 Device ID=0x..`が出ることも確認します。期待する子機が出ない場合は、最初にGateway群と子機の`group`が一致しているかを確認してください。

## 10. 現状の制約と注意点

- 群1〜7のGatewayでは、現状ダウンリンク機能が無効です。子機からGatewayへのアップリンク受信には使用できますが、Gatewayから子機への設定変更はできません。
- 既存の`0x01`〜`0x0F`の機器はすべて群0にそのまま収まるため、この体系への移行だけを理由に焼き直す必要はありません。
- 群分離は無線チャネルを変えず、GatewayがDeviceIDを見て自群以外を捨てるソフトフィルタ方式です。無線チャネル変更に伴う電波法対応コストを避けるため、この方式を採用しています。
- 現状、GatewayのLoRa受信は群方式ですが、BLE受信は既存ホワイトリスト方式のままです。BLE現場で群分離が必要な場合は、運用担当者だけで判断せず開発担当へ確認してください。
- XIAOを交換するとGatewayの`GW_DEVICE_ID`も変わります。交換時はID割当台帳とクラウド側の登録を更新してください。

## 1. 製品概要（用途・位置づけ・システム構成図）

**用途**: 現場に置いた複数の子機（Monita Flex / One / Deck）から 920MHz 帯 LoRa で計測データを受け取り、LTE-M でクラウド（Google Apps Script → Google スプレッドシート）へまとめて送る親機。スプレッドシートからの**遠隔操作**も中継する。対象は Gateway 本体の操作と、子機の設定変更（ダウンリンク）。

**位置づけ**: AC 電源（USB Type-C 給電）で常時動く据え置き機。子機は電池駆動で、送信するときだけ起きる。

```
[子機 Flex / One]  pkt 0x04 ─┐
[子機 Deck]  pkt 0x06 / 0x07 ─┤ 920MHz LoRa（E220-900T22S(JP)）
                              │   ↑ ダウンリンク 0x81（Flex）/ 0x82（Deck）
                              ▼
┌──────────── Monita Gateway（基板 ver1.21）────────────┐
│ XIAO nRF52840 ─ E220（LoRa 受信・ダウンリンク送信）      │
│              ├ SIM7080G（LTE-M Cat-M1、SIM 既定 1NCE） │
│              ├ DS3231（RTC。起動時に網時刻で補正）      │
│              ├ microSD（受信データ・動作ログ）          │
│              └ BLE（設定用コントローラー接続。LoRa 版）  │
└──────────────────────────────────────────────┘
                              │ HTTPS GET（LTE-M）
                              ▼
      Google Apps Script（gateway_common）── Google スプレッドシート
            │ 予約の受け渡し用に Google Drive のファイルも使う
            └─ メニュー［Gateway操作］［Flex操作］［Deck操作］
```

## 3. 子機の受信

### 3.1 対応子機・対応パケット（LoRa 版）

| 子機 | pktType | フレーム長 | 使うレコード数 | クラウドへの形式 | 根拠 |
|---|---|---|---|---|---|
| Monita Flex / Monita One | 0x04 | 19 B（厳密に一致） | 1 | 従来形式（`&pt=` なし） | G:394-399 |
| Monita Deck（静的 6CH 変位） | 0x06 | 21 B（厳密に一致） | 1 | `&pt=06` | 同上 |
| Monita Deck（イベント統計） | 0x07 | 22 B（厳密に一致） | 1 | `&pt=07` | 同上 |

- 長さが違うフレーム、チェックサムが合わないフレーム、知らない pktType は捨てる。捨てた件数は数えて、動作ログに出す（G:2995-3045）。
- 子機が使ってはいけない pktType: 0x05（Flex 用 ACK）、0x81（Flex 用ダウンリンク）、0x82（Deck 用ダウンリンク）、0x83（Deck 用 ACK）（G:376-382）。
- 新しい子機の型は、型の表（`SENSOR_FRAME_TYPES[]`）に 1 行足せば受信できる。受信、長さの検査、送信の分割はすべてこの表を見る（G:362-399）。GAS 側にも同じ型の処理が要る。
- Deck への対応は Gateway 側だけ実装済み。Deck 側のファームが未実装（S6〜S9）なので、Deck とつないだ通し試験はまだできない（試験一覧 B-10、G-C2、G-D3）。

### 3.2 最大台数とレコード数

| 項目 | 値 | 区分 | 根拠 |
|---|---|---|---|
| Gateway が一度に持てるレコード | 32 | 設計値 | G:444 |
| 1 群で使える DeviceID | 31（下位 5bit が 1〜31。0 は無効） | 設計値 | G:420-424 |
| Deck 1 台が使うレコード | 2（静的とイベント統計を別々に持つ） | 設計値 | G:3056-3066 |
| 例: Flex / One だけの場合 | 31 台（1 群の上限で決まる） | 設計値 | 上の 2 行 |
| 例: Deck だけの場合 | 16 台で 32 レコードが埋まる | 設計値 | 同上 |

- 1 レコードには**子機ごとの最新の 1 件だけ**を持つ。同じ子機から次のフレームが来ると上書きする（G:2202-2216）。
- 32 レコードが埋まった後に新しい子機のフレームが来ても、登録されずに捨てられる。警告は出ない（G:2208）。
- 送信に失敗して再送を待つデータも、次の送信では同じ 32 件の枠に入る。枠からあふれた分は捨てる（G:3855-3860）。

### 3.3 群（グループ）の考え方

同じ現場に Gateway を 2 台以上置くと、E220 の無線設定が全台で同じなので、どの Gateway も同じ子機を受信してしまう。これを避けるために DeviceID を分け、群が違う子機のフレームは Gateway のソフトで捨てる（G:286-307）。

```
DeviceID（1 バイト） = 群（上位 3bit, 0〜7） × 0x20 ＋ 群内番号（下位 5bit, 1〜31）
群 0 = 0x01〜0x1F、群 1 = 0x21〜0x3F、…、群 N = N×0x20+1 〜 N×0x20+0x1F
```

- Gateway の群はビルド時に `-D GATEWAY_GROUP_ID=n` で決める。起動ログの「設定サマリ」に群と、受け付ける DeviceID の範囲が出る（G:4328-4345）。
- どの群でもダウンリンクを使える。ただし群 1 以降では、群ごとの Drive ファイルを GAS とファームの両方に設定する必要がある（§9）。
- 無線のチャネルは全群で共通（REG2 = チャネル 0）。群で分けているのはソフトの受信判定だけで、電波の混雑は分けられない。
- BLE 版は群分けに対応していない。受信するのは、ホワイトリスト（0x01〜0x0F、pktType 0x03）に載っている子機だけ（G:331-360）。

### 4.4 クラウドへのデータの流れ

1. 子機のフレームを受けたら、Gateway は DS3231 の時刻（受信した時刻）と一緒に、子機ごとの最新の 1 件として持っておく。
2. 送信間隔ごとに、まず予約とコマンドを確認する。次に、受信した分を microSD（`gateway.csv`）に書く。それから型ごとに分けて、512 バイト以内の GET で GAS に送る（G:4869-4945、:3829-3990）。
3. GAS は DeviceID で製品の種類を判別し、子機ごとのシートに 1 件 1 行で書く。書く先は Flex / One なら `child_XX`（「シート名編集」で紐付け。紐付けがなければ `databox`）、Deck なら `deck_<HEX>` と `deck_<HEX>_event`（GC:1905-1945、:1270-1310）。
4. Gateway 自身の情報（起動時の info 行と、ステータス報告）は `databox` に書く（GC:2415-2445）。
5. シートの「計測日時」は、**子機の計測時刻ではなく、Gateway がそのフレームを受信した時刻**（GC:1905-1945）。
6. シートに届く項目は DeviceID、CH1〜4、LTE-M の CSQ、電池電圧（V2 形式のときだけ）。温度、Range、子機の FW 版、子機側の時刻はシートまで届かない（試験一覧 B-9）。

### 4.5 通信量の目安

| 項目 | 値 | 区分 | 根拠 |
|---|---|---|---|
| 1 日あたりの HTTPS 要求の回数 | 予約の確認が約 96 回で、1 回あたり GAS と Drive の 2 要求。これにデータ送信が 24 回 ×（件数 ÷ 15 を切り上げた回数）と、報告・ACK の分が加わる | 設計値（周期からの計算） | G:4025-4027、:282 |
| 月間の通信量（バイト） | 測っていない | 未確定 | 試験 G-C7 |

## 5. 遠隔操作

### 5.1 ダウンリンク（子機の設定変更の予約）— LoRa 版のみ

1. スプレッドシートのメニュー（［Flex操作］［Deck操作］）で予約を入れる。予約は GAS が持つ。
2. Gateway は約 15 分ごとに GAS へ `check_cmd` を送る。GAS は、自分の群の予約を Google Drive のファイルに書く。Gateway はそのファイルを読み、ワンタイム値（nonce）が一致した内容だけを手元に置く（G:1966-2046）。1 回に受け取れる予約は 20 件まで（GC:348）。
3. 子機のアップリンクを受けると、400ms 待ってからダウンリンクを送る。子機が受信を始める時刻に合わせた待ち時間（G:2715-2733、:2833-2870）。
4. 子機の確認応答（ACK）を受けて、初めて完了にする。適用された値と結果を GAS に報告し、シートに表示する。
5. 3 回送っても確認応答が返らなければ「未達」（status 99）にして打ち切る。子機が同じフレームを 2 回送ってくる分は、10 秒以内なら 1 回として数える（G:1447-1464）。

| 項目 | 値 | 区分 | 根拠 |
|---|---|---|---|
| Flex / One で変えられる設定 | 送信間隔、平均回数、メジアン回数、ステータスの確認のみ | 設計値 | G:2739-2780 |
| Deck で変えられる設定 | トリガ設定 13 バイト。時刻も毎回送る | 設計値 | G:1467-1502 |
| 同時に持てる予約 | 31 子機分 | 設計値 | G:1447 |
| 報告を貯めておける件数 | 32 件 | 設計値 | G:1543 |
| 反映までの時間 | 予約の確認周期（最大 18 分）＋子機が次に送信するまでの時間（子機の設定による）。届かなければ子機の周期ごとに再送する | 設計値 | G:4025-4027 |

### 5.2 リモートコマンド一覧（Gateway 本体）

スプレッドシートの［Gateway操作］メニュー、またはトークン付きの `set_cmd` で予約する。Gateway は次に `check_cmd` を送ったときに受け取る（最大約 18 分後。送信周期の間でも受け取る）。1 台の Gateway が保留できるコマンドは 1 件で、新しい予約で上書きされる（GC:2370-2378）。

| コマンド | 動作 | 根拠 |
|---|---|---|
| `reset` | 再起動する | G:2073-2077 |
| `stop` | GAS へのデータ送信だけを止める（受信と予約の確認は続ける）。再起動すると解除される | G:2078-2082 |
| `start` | データ送信を再開する | G:2083-2085 |
| `send_now` | 次の周期に、止めていても 1 回送る | G:2086-2089 |
| `interval:N` | 送信間隔を N 分（1〜1440）に変える | G:2090-2101 |
| `status_now` | CSQ、稼働時間、空きヒープを報告する | G:1366-1382 |
| `rtc_resync` | 網時刻で DS3231 を今すぐ補正する | G:1385-1393 |
| `log_dump` | `gwlog.csv` の末尾 180 バイトを GAS に送る | G:1397-1422 |

### 5.3 BLE コントローラー連携（LoRa 版のみ・暫定仕様）

デバイス名は `MonitaGateway`。GATT で次の 3 つを扱う（G:4093-4110、:4238-4270）。
- 送信間隔の書き込み（uint16、単位は分）
- コマンド: 0x01 = すぐ送信、0x02 = 網への再登録、0x03 = 起動確認の送信、0xFF = リセット
- ステータスの読み出し（14 バイト）

認証はない（§9）。

## 9. 使用上の制約・注意

**セキュリティ（現状、対策がないもの）**
- 無線のダウンリンク（0x81 / 0x82）と ACK（0x05 / 0x83）には認証も改ざん検知もない。偽のフレームや、過去のフレームの再送を区別できない（試験 C-X1）。
- GAS の各エンドポイントには、`set_cmd` 以外に認証がない。URL を知っていれば、データの送信、予約の取得、結果の報告ができる。`set_cmd` のトークンはソースに書かれた固定値。予約を受け渡す Drive ファイルは、リンクを知っていれば誰でも読める（試験 C-X2）。
- BLE コントローラー連携（LoRa 版）は認証なしで、送信間隔の変更やリセットができる（試験 C-X3）。

**容量とデータ**
- レコードは 32 件まで（§3.2）。Deck は 1 台で 2 件使う。枠を超えた子機のデータは、警告なしに捨てられる。
- Gateway は子機ごとに最新の 1 件しか持たない。送信間隔は子機の送信間隔以下にすること。
- 再送キューは RAM にあるので、停電や再起動で消える（試験 G-R4）。
- GAS が HTTP 200 で返す短いエラー（例: `ERROR: invalid d length`）は、Gateway 側では失敗と区別できない（GR:39-41）。
- `ack_cmd` の送信が成功すると、アプリ層 WDT の起点が更新される。このため、データ送信が止まっていても再起動が遅れることがある（試験 B-6）。

**構成・運用**
- GAS の宛先、SIM、群、Drive ファイルの ID はファームに書き込まれている。現場ごとにビルドして書き込む必要がある。書き込んだ後は、起動ログの「設定サマリ」で確認すること（G:4328-4400）。
- 群 1 以降でダウンリンクを使うときは、群ごとの Drive ファイルを作る。そして GAS（`DOWNLINK_DRIVE_FILE_IDS`）とファーム（`-D DOWNLINK_DRIVE_FILE_ID`）の両方に同じ ID を設定する。現在登録してあるのは群 0 だけ（GC:57-60、G:309-325）。設定が食い違うと、テレメトリは届くがダウンリンクだけが届かなくなる。
- XIAO を交換すると、Gateway の ID（`gw_<XIAO固有ID>`）が変わる。GAS の台帳の更新が必要（G:1312-1330）。
- 1 つの GAS で、One と Deck が混在する現場は扱えない（試験 B-8）。One PIR の ACK（14 バイト）は受け付けない（試験 B-4）。
- microSD のログは古いものから消す仕組み（ローテーション）がない。容量がいっぱいになったときの挙動は試験していない（試験 G-B3）。
- 未受信の警告メール（60 分）を使うには、GAS 側でトリガと送信先（`ADMIN_MAILS`）の設定が要る（GC:906-912、:2590-2641）。
- 1NCE 以外の SIM を使う場合は、APN を確定してからビルドする。

**BLE 版の制限**（BLE 版はビルド時に選ぶ代替構成）
- ダウンリンク、群分け、コントローラー連携、送信間隔の保存は使えない。受信するのは Flex BLE（pktType 0x03、19 バイト）で、DeviceID のホワイトリスト（0x01〜0x0F）に載っているものだけ。

**検証状況**
- 基板 ver1.21 と FW 98 以降の組み合わせは、ビルドまでしか確認していない（試験 G-B1）。Deck との通し試験はできない状態（§3.1）。

## 付録A. 受信・送信データ形式（概要）

**A.1 LoRa の無線フレーム（子機と Gateway の間で共通）**
`[0xAA][LEN][本体 LEN バイト][SUM]`。SUM は 0xAA、LEN、本体を足した値の下位 8bit。受信時は、E220 が末尾に RSSI バイトを 1 つ付け足す（dBm = 値 − 256）。

**A.2 子機からのデータ（本体）**

| 型 | 長さ | 並び |
|---|---|---|
| 0x04 Flex / One | 19 | [0]0x04 [1]DeviceID [2]FW [3-10]CH1〜4（int16 LE） [11-12]電池電圧 mV [13]時 [14]分 [15-18]CH1〜4 のレンジ |
| 0x06 Deck 静的 | 21 | [0]0x06 [1]DeviceID [2..]Deck 側の定義に従う（Gateway は中身を解釈しない） |
| 0x07 Deck イベント統計 | 22 | 同上 |

**A.3 ダウンリンクと確認応答**

| 型 | 向き | 長さ | 並び |
|---|---|---|---|
| 0x81 Flex | Gateway → 子機 | 15 | [0-1]0xC0DE [2]0x81 [3]宛先 ID [4]Flags [5-10]YY MM DD hh mm ss [11-12]送信間隔（分、BE） [13]平均回数 [14]メジアン回数 |
| 0x05 Flex ACK | 子機 → Gateway | 7 / 9 | [0]0x05 [1]ID [2]status [3-4]適用した間隔（BE） [5]平均 [6]メジアン [7-8]WDT（分、BE。9 バイトのときだけ） |
| 0x82 Deck | Gateway → 子機 | 24 | [0-1]0xC0DE [2]0x82 [3]宛先 ID [4]Flags [5-10]時刻（JST） [11-23]トリガ設定 13 バイト |
| 0x83 Deck ACK | 子機 → Gateway | 17 | [0]0x83 [1]ID [2]status [3]子機の FW [4-16]適用したトリガ設定 13 バイト |

- Flags: bit0 = 時刻、bit1 = 送信間隔、bit2 = 平均とメジアン、bit3 = Deck のトリガ。Flex では bit1 と bit2 を立てる（ステータス確認では 0）。Deck では bit0 と bit3 を立てる。
- status: 0 = OK、1 = 範囲外、2 = 丸めて適用、99 = 未達（Gateway が付ける）。
- 出典: G:2695-2715、:1461-1502、:2739-2810。

**A.4 Gateway から GAS へ送るデータ行（HTTPS GET のクエリ）**
`q=<CSQ, 16進 2 桁>[&pt=06|07]&n=<件数>&d=<レコードを続けた 16進文字列>`
- Flex / One の既定形式: 1 件 13 バイト（16 進 26 文字）。並びは Epoch（4 バイト、LE、UTC、Gateway が受信した時刻）＋ DeviceID ＋ CH1〜4（8 バイト）。
- V2 形式（`-D CLOUD_FMT_V2`）: 上の末尾に電池の値を 1 バイト足す（mV = 3000 + 値 × 5。255 は未取得）。1 件 14 バイト。
- Deck: 1 件 = Epoch（4 バイト）＋ 本体の [1] 以降。0x06 は 24 バイト（48 文字）、0x07 は 25 バイト（50 文字）。
- 1 回の GET に入れるのは同じ型だけ。URL は 512 バイト以内（G:3680-3806）。

**A.5 そのほかの要求**
`row_type=info`（起動時）、`action=check_cmd&dl=1&group=N&nonce=…`、`ack_cmd`、`downlink_sent`、`downlink_result`、`status_report`、`log_dump`（G:3614-3645、:2020-2072、:1882-1930）。

**A.6 予約行（Drive ファイルの 2 行目以降）**
`HEX2:送信間隔:平均:メジアン:試行回数:seq:mode[:トリガ設定16進26文字]`。フィールドが 8 個あれば Deck、7 個なら Flex（GR:129-136）。

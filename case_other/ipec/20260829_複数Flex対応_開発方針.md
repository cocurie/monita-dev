# iPEC連携：複数Flex対応・開発方針

## 背景（要望）

iPEC社のクラウドサーバーは**1回のHTTP受信を1つのデータの塊として認識する**。
Flexを複数台（当面2台）運用する場合、各Flexのデータを**個別に分けて複数回のPOSTで送る**必要がある。

連携先（iPEC）のサーバーはこちらで触れないため、振り分け・分割はこちら側（Gateway）で行う。

## 前提の確認：この連携はGASを経由しない

`01_http_post/README.md`・`src/main.cpp`で確認した実際の構成は以下の通り。

```
Flex（test_sketches/18_lora_child、LoRa送信）
   ↓
Gateway（case_other/ipec/01_http_post、独立ファーム）
   ├─ LoRa受信
   └─ SIM7080Gの生TCP+SSL（AT+CAOPEN/AT+CASEND）でiPECへ直接POST
```

自社GAS（`case02_Gateway/gas/`）は使われていない。理由はコード内コメントに明記されている：
SIM7080GのSHHTTPクライアント（`AT+SHBOD`等）はJSON内のダブルクォートを扱えないため、
生HTTPリクエストを組み立てて送る方式を採用している。

したがって、DeviceID群分離プロジェクト（`case02_Gateway/firmware/gateway_v1.20`・
`case02_Gateway/gas/`）とは**アーキテクチャが独立**しており、直接の依存関係はない。

## 開発方針：ファームは分ける（既に分かれている）

`case_other/ipec/01_http_post/`は、共通のGatewayファーム（`gateway_v1.20`）とは別の
**独立したGatewayスケッチ**である。これは`project07_NEXCO`・`project06_yokogawa`と同じ
「案件ごとに独立コピーする」既存パターンを踏襲したもの。

**今回の対応も、この独立ファームの中だけで完結させる。** 共通コード
（`case02_Gateway/firmware/gateway_v1.20`・`case01_Flex/v3.20`）や、
DeviceID群分離の実装には一切手を入れない。

## 必要な変更

### Gateway側（`case_other/ipec/01_http_post/src/main.cpp`）

現状は1台のFlexしか想定していない。

```cpp
static const uint8_t TARGET_DEVICE_ID = 0x0E;  // 1台固定
static bool     s_newFrameReady = false;        // 受信バッファも1台分だけ
static int16_t  s_rxCh[4];
static uint16_t s_rxBatt;
```

`loop()`は「LoRaフレームを1つ受信 → JSON1つ作る → POST1回」という単位で動作しており、
**複数台分をまとめて1回のPOSTにする処理はそもそも存在しない**。つまり「1台ずつ分けて送る」
という要件は、対象デバイスを1台から複数台に広げるだけで自然に満たせる（分割ロジックの
追加は不要）。

具体的な変更点:

1. `TARGET_DEVICE_ID`を配列化する（例: `{0x0E, 0x0F}`）。受信フレームの`deviceId`が
   このリストに含まれるかで判定するよう`loraPoll()`を変更する
2. 受信バッファ（`s_rxCh`/`s_rxBatt`/`s_newFrameReady`等）を**デバイスごとに1組ずつ**
   持つ（小さな構造体配列で足りる。台数分の受信窓が同時に埋まってもPOST漏れしないように）
3. JSON内の`"device"`フィールドが現状`"monita-flex-001"`固定。iPEC側でデバイスを
   区別する必要があるなら、DeviceID→iPEC登録済みデバイス名のマッピングに変える
4. 各デバイスのフレームが届くたびに、それぞれ独立して`postToIpec()`を呼ぶ
   （既存のPOST単位は変更しない）

### Flex側（`case01_Flex/test_sketches/18_lora_child`）

確認の結果、`DEVICE_ID`が**ハードコードされている**（`static const uint8_t DEVICE_ID = 0x0E;`、
`src/main.cpp:59`）。`case01_Flex/v3.20`で先に対応したような
`#ifndef DEVICE_ID` ビルド時上書き方式には未対応。

2台目を焼くために毎回ソースを書き換える運用は焼き忘れ・戻し忘れの事故につながるため
（v3.20をマクロ化した際と同じ理由）、この機会に同様のマクロ化を行うことを推奨する。

```c
#ifndef DEVICE_ID
#define DEVICE_ID 0x0E
#endif
```

ペイロード形式（DeviceID・CH1-4・電池電圧の19バイト固定）自体は共通で変更不要。

## スコープ外（今回は対応しない）

- `case02_Gateway/firmware/gateway_v1.20`・`case02_Gateway/gas/`（DeviceID群分離プロジェクト本体）
- `project07_NEXCO`・`project06_yokogawa`の独立ファーム
- iPEC側サーバーの仕様変更（触れられないため対象外）
